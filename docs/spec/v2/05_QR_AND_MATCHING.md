# 05 受諾ロックとQR完了

## 原子的な受諾
`POST /requests/{id}/accept` のサーバーDB transaction: 行ロック→`open`/期限/供給者契約/公開サービス/資格/営業エリア/スタッフ・カレンダー整合を検証→ `accepted_supplier_id` と状態、受諾条件スナップショット、イベント/outboxを一回だけ更新。条件付き `UPDATE ... WHERE status='open' RETURNING ...` でもよい。ユーザーの連打はIdempotency-Keyで同一結果。別会社の同時受諾は409。受諾者にのみ詳細住所を開示。企業管理者は自社スタッフに担当を割当、受諾元企業の変更は不可。

## 推薦とUber型の運用
供給者の対応カテゴリ、資格、可用時間、対応地域、停止状態を先に絞る。ETA/移動方向/空き時間/本人の選好/品質/公平性で順位付け。「近い」「対応時間内」「必要資格あり」と理由を表示。推薦は自動契約でなく、供給者本人の受諾でのみロック。供給者への通知は限定配信→一定時間後に拡大。未受諾なら期限で通知拡大/顧客へ再設定提案。進行追跡、連絡、キャンセル、評価。実測位置の常時共有は必要な業務時間のみ。機密住所は公開一覧に出さない。

## QR仕様
完了申請状態で顧客の認証済iOS端末のみQR発行。`token` はCSPRNGで生成する256bitのランダム値、QRにはURL/電話/住所を含めずOpaque tokenだけを格納（ASCII `HD1:` + base64url）。サーバーはtokenのハッシュ、request_id、customer_id、accepted_supplier_id、assigned_staff_id、expires_at、consumed_atを保存。1トークン60秒・再発行時に前token無効化。顧客が実施内容と問題なしを確認後に表示、閉じると表示終了。スキャナはログインした供給者企業に割当済みの担当者だけ利用。

読取後のonline `POST /requests/{id}/qr/verify`: 認証・担当者と組織・依頼状態・hash・期限・未使用・契約有効性をDBトランザクションで確認し、`consumed_at` と `completed`、quota消費、必要な精算イベントを一回だけcommit。2台からの同時読取は一方のみ成功。スクリーンショットの再使用・別依頼・別供給者・期限切れ・予約取消のcodeは拒否。カメラの標準QR認識を用い、外部URLを開かない。電波がない場合は完了扱いにせず、復帰後新QRを表示する。位置チェックは補助証跡で、位置だけで完了しない。サーバー応答で双方に成功画面/履歴を表示。顧客が作業に問題を報告するとQR発行不可でdisputed。

## 例外
顧客不在/端末故障なら供給者は証跡を提出して運営へ申請。顧客へ通知し、二名の運営承認で `resolved_completed` または取消/差戻し。スタッフによる顧客アカウント代理ログインやQRの自作は禁止。完了トークン・個人情報をログ/分析に含めない。試行回数制限、異常頻度/位置乖離のアラート。
